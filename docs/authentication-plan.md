# Аутентификация пользователей с PostgreSQL и GORM

## Summary

Реализовать регистрацию, вход, обновление токенов и выход на Go + PostgreSQL. Для ORM использовать **GORM v2** с официальным PostgreSQL-драйвером `gorm.io/driver/postgres`: он поддерживает PostgreSQL через `pgx`, транзакции, блокировки строк и контекст запросов — это необходимо для безопасной ротации refresh-токенов. [Документация GORM для PostgreSQL](https://gorm.io/docs/connecting_to_the_database.html)

## Implementation Changes

- Подключить зависимости: `gorm.io/gorm`, `gorm.io/driver/postgres`, JWT-библиотеку и bcrypt.
- Инициализировать единый `*gorm.DB` из `DATABASE_URL`, проверить подключение при старте, настроить пул соединений и передать БД в репозитории приложения.
- Описать GORM-модели и миграции для:
  - `users`: UUID, уникальный нормализованный email, bcrypt-хэш пароля, даты создания/обновления;
  - `refresh_sessions`: UUID, пользователь, SHA-256-хэш refresh-токена, срок действия, дата отзыва/замены и даты создания/обновления.
- Миграции выполнять явно при запуске приложения через GORM migrator; не использовать `AutoMigrate` как единственный механизм production-изменений схемы. Индексы и внешние ключи задать в миграциях.
- В репозитории использовать GORM для CRUD и транзакцию с блокировкой refresh-сессии при обновлении: старая сессия помечается отозванной, новая создаётся в той же транзакции. GORM предоставляет транзакции и SQL-построитель, поэтому при необходимости можно использовать точечный SQL без второго драйвера. [Возможности GORM](https://gorm.io/docs/)
- Добавить маршруты:
  - `POST /auth/register` — создаёт пользователя, возвращает `{accessToken, user}` и устанавливает refresh-cookie;
  - `POST /auth/login` — проверяет email/пароль, выдаёт новую пару токенов;
  - `POST /auth/refresh` — ротирует refresh-сессию и возвращает новый access JWT с безопасным `{id, email}` пользователя;
  - `POST /auth/logout` — отзывает текущую сессию и очищает cookie.
- Использовать bcrypt; нормализовать email; принимать пароль от 8 символов. Access JWT подписывать HS256 и включать `sub`, `iss`, `iat`, `exp`, `jti`.
- Access JWT действует 1 день. Refresh-токен действует 30 дней, передаётся только в `HttpOnly`, `Secure`, `SameSite=Strict` cookie с путём `/auth`. Каждый refresh выдаёт новый refresh-токен и продлевает сессию ещё на 30 дней.

## API and Error Contract

- Регистрация возвращает `201`, вход и refresh — `200`, logout — `204`.
- Ошибки валидации — `400`, занятый email — `409`, неверные данные входа или недействительный/повторно использованный refresh — `401`.
- В API никогда не возвращается password hash или refresh-токен в JSON.
- Повторное использование прежнего refresh-токена не выдаёт новую пару токенов.

## Assumptions

- В v1 нет подтверждения email, восстановления пароля, ролей и завершения всех сессий пользователя.
- Refresh-cookie использует `SameSite=Strict`. Для прямых запросов frontend к API настроен credentialed CORS с одним явным origin через `CORS_ALLOWED_ORIGIN`.
