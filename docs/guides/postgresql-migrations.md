# Гайд по миграциям PostgreSQL

Этот документ описывает текущий механизм миграций в `uptime-app` и обязательный порядок действий при изменении схемы. Он предназначен в том числе для агентов: не предполагает существование отдельного CLI миграций или таблицы версий.

## Как миграции работают сейчас

Миграция запускается при каждом старте API:

1. `backend/internal/app/app.go` создаёт подключение к PostgreSQL.
2. Затем вызывает `repository.Migrate(ctx, db)`.
3. `backend/internal/repository/migrate.go` выполняет все шаги в одной транзакции.
4. Если шаг завершается ошибкой, API не начинает обслуживать запросы.

В проекте **нет** таблицы учёта версий миграций и отдельной команды мигратора. Поэтому каждый новый шаг должен быть безопасен при повторном запуске: проверять наличие таблицы, столбца или другого объекта перед изменением и не повреждать уже перенесённые данные. `AutoMigrate` не используется как замена явной production-миграции.

## Где находится всё необходимое

| Что | Расположение | Назначение |
| --- | --- | --- |
| GORM-модели | `backend/internal/model/auth.go` | Описывают текущие таблицы, типы, индексы и внешние ключи для `users`, `refresh_sessions` и `monitors`. |
| Шаги миграции | `backend/internal/repository/migrate.go` | Единственное место для явных изменений схемы и данных. |
| Открытие PostgreSQL | `backend/internal/repository/postgres.go` | Подключение и проверка доступности БД. |
| Запуск миграции | `backend/internal/app/app.go` | Вызывает `Migrate` до создания репозиториев и HTTP-сервера. |
| Интеграционный тест | `backend/internal/repository/migrate_integration_test.go` | Проверяет создание схемы в PostgreSQL и базовые операции репозиториев. |
| Настройки окружения | `backend/internal/config/config.go`, `backend/README.md` | `DATABASE_URL` нужен приложению; `TEST_DATABASE_URL` — только для выделенной тестовой БД. |

## Шаблон описания миграции

Перед изменением `migrate.go` заполните в задаче или PR:

- **Цель:** что именно меняется в схеме и зачем.
- **Затронутые объекты:** таблицы, столбцы, индексы, ограничения и данные.
- **Совместимость:** смогут ли существующие записи и текущая версия приложения работать во время развёртывания.
- **Преобразование данных:** какие старые значения нужно заполнить или привести к новому виду; почему операция повторяема.
- **Откат и риск:** можно ли безопасно откатить изменение; нужны ли резервная копия, поэтапный релиз или ручная операция.
- **Проверка:** какой тест покрывает переход со старой схемы и какие запросы подтверждают результат.

Если изменение удаляет данные, переименовывает столбец, сужает тип или добавляет обязательное ограничение к заполненной таблице, не добавляйте его автоматически в стартовую миграцию без отдельного плана и явного согласования. Сначала используйте совместимый этап: добавить новое поле, заполнить его, переключить код и только затем удалить устаревшее.

## Порядок внесения изменений

1. Изучите текущую модель и `Migrate`. Установите, требуется ли новая таблица, аддитивный столбец, индекс, ограничение или перенос данных. Не полагайтесь только на тег модели: он не меняет существующую production-схему сам по себе.

2. Обновите GORM-модель в `backend/internal/model/`. В тегах задайте тип, обязательность, индекс и внешние ключи для **новой** таблицы. Это обеспечивает правильное создание чистой БД через `CreateTable`.

3. Добавьте явный идемпотентный шаг в `backend/internal/repository/migrate.go` внутри уже существующей транзакции.

   Для новой таблицы используйте проверку и `CreateTable`:

   ```go
   if !migrator.HasTable(&model.Example{}) {
       if err := migrator.CreateTable(&model.Example{}); err != nil {
           return fmt.Errorf("create examples table: %w", err)
       }
   }
   ```

   Для нового обязательного столбца в существующей таблице добавляйте его поэтапно: временный default или nullable-вариант, заполнение старых строк, затем финальное ограничение. Проверяйте наличие столбца до `ALTER TABLE`, а ошибки оборачивайте с названием операции. Используйте точечный PostgreSQL SQL через `tx.Exec`, как это сделано для `users.name` и `users.avatar_filename`.

4. Если меняются данные, сделайте преобразование повторяемым. Условие `UPDATE` должно пропускать уже обработанные строки. Пример существующего подхода — добавление префикса `avatars/` только к непустым значениям без `/`.

5. Для индексов, внешних ключей и иных изменений существующей схемы добавьте отдельную явную проверку и шаг мигратора либо SQL. Не рассчитывайте, что `CreateTable` исправит объект в уже созданной таблице.

6. Не выносите миграцию в обработчик, сервис или репозиторий CRUD. Порядок должен оставаться централизованным в `Migrate`, чтобы он выполнялся до начала работы API.

## Проверка миграции

### Автоматические проверки

Из каталога `backend/` выполните:

```bash
go test ./...
go vet ./...
```

Обычный запуск тестов может пропустить PostgreSQL-интеграционный тест, если не задан `TEST_DATABASE_URL`. Для реальной проверки используйте **отдельную одноразовую тестовую БД**: тест удаляет и заново создаёт `users`, `refresh_sessions` и `monitors`.

```bash
TEST_DATABASE_URL='postgresql://...' go test ./internal/repository -run TestMigratePostgreSQLAndRotateSession -count=1
```

Никогда не передавайте в `TEST_DATABASE_URL` development-, staging- или production-базу с нужными данными.

Для каждого нового шага расширьте интеграционное покрытие так, чтобы оно проверяло именно этот переход. Текущий тест подтверждает создание чистой схемы, но сам по себе не доказывает корректное обновление БД со старой версией таблицы. При миграции существующего столбца или данных создайте в тесте предыдущую схему и записи, вызовите `Migrate`, затем проверьте новую структуру и преобразованные значения.

### Ручная проверка на тестовой или staging-БД

1. Сделайте резервную копию БД, если среда содержит ценные данные.
2. Запустите API с её `DATABASE_URL`. Старт API сам выполнит миграцию; успешный запуск означает, что `Migrate` завершился без ошибки.
3. Перезапустите API. Повторный запуск обязан пройти без ошибки и без повторного преобразования данных.
4. Проверьте таблицы, столбцы, индексы и ограничения через клиент PostgreSQL. Например, в `psql`:

   ```sql
   \d+ users
   \d+ refresh_sessions
   \d+ monitors
   ```

5. Проверьте доменный сценарий, который использует изменённую схему: создание, чтение и обновление записи; для переноса данных — несколько старых и уже перенесённых значений.
6. Сверьте количество и содержимое преобразованных строк с ожидаемыми данными. Не выполняйте массовые запросы изменения данных вручную в production, если они не являются частью согласованного плана миграции.

## Итоговый чек-лист

- [ ] Модель и явный шаг в `Migrate` согласованы между собой.
- [ ] Шаг находится внутри транзакции и возвращает понятную ошибку.
- [ ] Повторный запуск безопасен: проверены существующие объекты, данные не преобразуются повторно.
- [ ] Для существующих данных предусмотрены заполнение, совместимость и проверка результата.
- [ ] Опасные операции не запускаются автоматически при старте API без отдельного согласованного плана.
- [ ] Добавлен или обновлён PostgreSQL-интеграционный тест перехода схемы.
- [ ] Выполнены `go test ./...` и `go vet ./...`; интеграционный тест запускался с выделенной `TEST_DATABASE_URL`.
- [ ] На тестовой или staging-БД подтверждены схема, данные, доменный сценарий и успешный повторный старт API.
